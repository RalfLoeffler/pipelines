# ProtocolQC Template Workbook Limitations and Compatibility Notes

**Document purpose:** record limitations of the current XNAT template-generation notebook/workbook and identify what must be ported from the supplied Flywheel ProtocolQC code before generated templates can be treated as production-equivalent.

**Generated:** 2026-07-22T05:32:38.371337+00:00

## Source basis

This document is based on the supplied files:

- `save_protocol_fw.py`: Flywheel script that creates the approved protocol JSON template from a reference Flywheel session.
- `run.py`: Flywheel ProtocolQC gear implementation that performs DICOM parameter extraction, protocol comparison, multi-echo handling, file-count checks, tagging, and notification side effects.
- `PROTOCOLQC_CREATE_TEMPLATE_FROM_XNAT.ipynb`: current XNAT notebook/workbook prototype for creating a ProtocolQC template from an XNAT reference session.

## Current status of the XNAT workbook

The current notebook is useful for proving the XNAT-side workflow:

1. Connect to XNAT.
2. Select a reference project, subject, and session.
3. Download scan-level DICOM resources.
4. Assemble a ProtocolQC-style JSON template.
5. Add default tolerances.
6. Optionally upload the JSON to the project-level `ProtocolQC/protocol-template.json` resource.

However, the notebook currently relies on the simplified ProtocolQC scaffold functions:

```python
read_dicom_headers(...)
combine_dicom_parameters(...)
```

It does **not** yet use a full XNAT-independent port of the Flywheel extraction functions:

```python
run.return_dicom_dict(...)
run.combined_dicom_dicts(...)
```

Therefore, the notebook should currently be treated as an **XNAT access and template-assembly prototype**, not as a production-equivalent replacement for the Flywheel template generator.

## Already mentioned in the workbook

The existing workbook contains a high-level warning that the DICOM extractor is still a scaffold and that enhanced MR functional groups, Siemens private tags, Phoenix parsing, spectroscopy, phase-encoding polarity, and full Flywheel compatibility remain TODOs.

The sections below expand that warning into specific compatibility limitations.

## Detailed limitations

### 1. Full Flywheel DICOM extraction has not been ported

The Flywheel template generator delegates DICOM interpretation to functions in `run.py`, especially:

```python
run.return_dicom_dict(...)
run.combined_dicom_dicts(...)
```

The XNAT workbook currently calls the simplified scaffold extraction instead. This means the XNAT-generated template may contain missing, simplified, or incompatible values compared with a template generated by the Flywheel tool from the same DICOM data.

**Impact:** values that should come from enhanced MR functional groups or Siemens private tags may be written as `NA`, omitted, or derived from non-equivalent public DICOM fields.

### 2. Enhanced MR functional-group parsing is incomplete

The Flywheel implementation reads acquisition parameters from enhanced MR structures such as:

- Shared Functional Groups Sequence `(5200,9229)`
- Per-frame Functional Groups Sequence `(5200,9230)`
- MR Timing and Related Parameters Sequence `(0018,9112)`
- MR Modifier Sequence `(0018,9115)`
- MR Receive Coil Sequence `(0018,9042)`
- MR FOV/Geometry Sequence `(0018,9125)`
- Pixel Measures Sequence `(0028,9110)`
- MR Echo Sequence `(0018,9114)`
- MR Image Modifier Sequence `(0018,9006)`
- MR Frame Type Sequence `(0018,9226)`

The current scaffold extracts mostly stable public/top-level DICOM attributes. Enhanced MR datasets may store the required values in nested functional groups rather than top-level tags.

**Impact:** generated protocol fields such as TR, TE, TI, flip angle, bandwidth, coil, pixel spacing, slice thickness, phase-encoding direction, and geometry-derived fields may not match Flywheel output.

### 3. SOP Class handling is not equivalent

The Flywheel code explicitly handles or rejects several SOP Class cases, including:

- Enhanced MR Image Storage
- MR Spectroscopy Storage
- Regular MR Image Storage
- Phoenix ZIP report-related structured-report handling
- unsupported SOP classes

The current workbook does not reproduce those decisions in full.

**Impact:** unsupported or regular non-enhanced MR DICOM may be processed differently by the XNAT workbook than by the Flywheel gear. This can produce templates that later fail QC, produce false deviations, or hide unsupported input types.

### 4. Derived-image filtering is not equivalent

The Flywheel extraction checks `ImageType` and skips images containing `DERIVED`.

The current workbook does not yet guarantee the same per-header derived-image filtering.

**Impact:** derived images may influence the generated template if present in XNAT scan resources.

### 5. Siemens private-tag handling is incomplete

The Flywheel code reads Siemens private structures and Phoenix protocol text to derive values such as:

- `Sequence`
- `Sequence_options`
- `PE_polarity`

The current workbook does not yet implement the full private-tag and Phoenix parsing behaviour.

**Impact:** Siemens-specific protocol fields may be missing or not comparable with historical approved templates generated by the Flywheel tool.

### 6. Phase-encoding polarity is not implemented

The Flywheel code derives `PE_polarity` by parsing Phoenix protocol content such as:

```text
sSliceArray.asSlice[0].dInPlaneRot
```

The scaffold currently does not reproduce this calculation.

**Impact:** `PE_polarity` may remain `NA` or incorrect in the generated XNAT template.

### 7. Spectroscopy fallbacks are incomplete

The Flywheel implementation includes fallback objects for cases where spectroscopy data do not contain all image-oriented enhanced MR structures.

The current workbook does not yet reproduce all of those fallback paths.

**Impact:** MR spectroscopy inputs may fail extraction or produce incomplete templates.

### 8. Calculated geometry fields are missing or simplified

The Flywheel output dictionary includes calculated fields such as:

- `freq_fov`
- `phase_fov`
- `Freq_row`
- `Freq_col`
- `Phase_row`
- `Phase_col`
- `Slice_Gap`
- `Freq_res`
- `Phase_res`

The current scaffold either does not compute all of these values or computes simplified values.

**Impact:** templates generated by the XNAT workbook may not include the same acquisition fields as the Flywheel dictionaries.

### 9. Multi-echo combination behaviour is not fully equivalent

The Flywheel function `combined_dicom_dicts(...)` compares each DICOM header against the first header in the series and turns differing acquisition values into lists. It also updates:

```text
Sequence_Attributes.Multi-Echo
```

based on the number of distinct values.

The current XNAT scaffold has only partial value-combination behaviour.

**Impact:** multi-echo series and series with per-frame/per-file differences may not generate the same approved template structure as the Flywheel script.

### 10. DICOM file-count multiplier semantics are not fully implemented

The Flywheel QC comparison later uses:

- `Check_DICOM_File_Number`
- `Temporal_positions_multiplier`
- `Echo_lines_multiplier`
- `Multi-Echo`
- `Temporal_positions`

when checking the expected number of DICOM files in a series.

The current XNAT template creator records sequence attributes but does not yet reproduce or validate the full downstream file-count semantics.

**Impact:** generated templates may require manual editing before file-count checks can be trusted.

### 11. Phoenix ZIP report handling is not ported

The Flywheel gear contains special handling for acquisitions labelled `PhoenixZIPReport`, including extraction of protocol names from Siemens header text and checking those names against the template `SequenceList`.

The current XNAT workbook does not implement an equivalent Phoenix ZIP report workflow.

**Impact:** template sequence completeness checks based on Phoenix ZIP reports are not yet available in the XNAT workflow.

### 12. Metadata fields are intentionally changed for XNAT

The Flywheel template contains Flywheel-specific metadata fields, including phone-list and SMS-related fields.

The XNAT workbook intentionally replaces those with XNAT source metadata such as project, subject, session, and generation time.

**Impact:** this is an intentional divergence, but it should be documented so future compatibility tests do not treat this as an accidental mismatch.

### 13. Flywheel side effects are intentionally excluded

The following Flywheel behaviours are not part of the XNAT workbook and should not be ported directly:

- Flywheel session tags
- Flywheel project attachments
- Gear Toolkit paths
- Twilio SMS notifications
- `/flywheel/v0/output`

XNAT-native replacements, if needed, should be designed separately.

### 14. XNAT resource assumptions still need validation

The workbook assumes the reference session’s scan-level DICOM resources can be downloaded as ZIP archives from XNAT and that the generated JSON can be uploaded to a project-level resource.

These assumptions must be validated in the local XNAT sandbox and the real AIS-XNAT deployment.

**Impact:** resource labels, permissions, project IDs, session labels, scan types, and archive layouts may differ between XNAT deployments.

## Risk summary

Until the full Flywheel extraction logic is ported and tested, an XNAT-generated template may:

- omit required acquisition fields;
- contain `NA` where Flywheel would extract a value;
- produce different sequence dictionaries from the same DICOM;
- mishandle enhanced MR DICOM;
- mishandle spectroscopy;
- mishandle Siemens private metadata;
- miss phase-encoding polarity;
- misrepresent multi-echo sequences;
- require manual correction of file-count multiplier fields;
- produce false PASS or false FAIL results when used by the ProtocolQC pipeline.

## Required implementation work before production use

1. Port `return_dicom_dict(...)` into `protocol_qc/dicom.py` without Flywheel side effects.
2. Port `combined_dicom_dicts(...)` into `protocol_qc/dicom.py` without Flywheel context dependencies.
3. Remove calls to Flywheel tagging and SMS logic from extraction paths.
4. Replace broad exception suppression with structured warnings in the report.
5. Make the XNAT workbook call the same shared extraction module as the runtime ProtocolQC pipeline.
6. Add regression tests comparing XNAT extraction output with Flywheel extraction output on the same DICOM fixtures.
7. Add enhanced MR, spectroscopy, Siemens private-tag, Phoenix ZIP, multi-echo, and file-count fixtures.
8. Validate the generated template in the local XNAT sandbox before uploading to any real project.

## Required review before approving a generated template

Before using a generated `protocol-template.json` as an approved template, manually review:

- `Metadata.DictionaryVersion`
- `Metadata.SequenceNumber`
- `Metadata.SequenceList`
- every sequence description key
- duplicate sequence descriptions and numbered alternatives
- `Sequence_Attributes.Ordinal_Number`
- `Sequence_Attributes.Multi-Echo`
- `Sequence_Attributes.Check_DICOM_File_Number`
- `Sequence_Attributes.Temporal_positions_multiplier`
- `Sequence_Attributes.Echo_lines_multiplier`
- all numeric tolerances
- fields with value `NA`
- missing calculated geometry fields
- missing Siemens-specific fields
- missing Phoenix-derived fields
- expected handling of scouts, localisers, reports, derived images, and optional sequences

## Recommended next step

The next code change should be to port the Flywheel extraction logic into the shared ProtocolQC source module and update the workbook so it imports that same module. The workbook should remain responsible only for XNAT download, template assembly, human review, and optional upload.
